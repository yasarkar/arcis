# AGENTS.md

Guidance for agents working in this repo (Arcis / `arc-mini-app`, Arc Testnet chain ID 5042002).

## Arc & CCTP bridging — verified facts

- **Arc Testnet bridging is not USDC-only.** Standard CCTP moves USDC (every CCTP domain except BNB Smart Chain); "CCTP for non-USDC" adds EURC plus configurable tokens (cirBTC, WETH). Arc's CCTP domain is `26` for both paths. Gateway's unified balance is USDC-only.
  - Sources: https://docs.arc.io/integrate/exchanges/cctp-bridging, https://developers.circle.com/cctp/expanded-assets/concepts/supported-chains-and-domains
- **Non-USDC CCTP routes are EVM-only** (Solana unsupported) and route-specific: both domains must trust each other and the token must be configured on both. Don't assume a token works on a route — check `https://iris-api-sandbox.circle.com/v2/cctpx/tokens`.
- **Local EVM simulators cannot validate Arc bridging** — Arc docs state they don't replicate EIP-7708 `Transfer` events, the USDC precompile, or blocklist enforcement. Test against Arc Testnet only.
- **`docs.arc.network` redirects to `docs.arc.io`** — the live docs host is `docs.arc.io` (skills and root `llms.txt` still use the old hostname).

## Repo conventions & quirks

- **`llms.txt` at the repo root is Arc's docs index, not project documentation.**
- **Circle skills are duplicated byte-for-byte** in `.agents/skills/` and `skills/plugins/circle/skills/` (17 shared skills, verified identical). Apply any Circle skill edit to both; `.agents/skills/` additionally carries 7 non-Circle skills (`banner-design`, `brand`, `design`, `design-system`, `slides`, `ui-styling`, `ui-ux-pro-max`) that exist only there.
- **Bridge tab chains are intentionally narrower than Gateway's**: `BRIDGE_SELECTABLE_CHAINS` filters out Solana (balances, delivery verification and address handling on that surface are EVM-only), though Solana remains in `GATEWAY_SUPPORTED_CHAINS`.
- **Dependency changes need the Vite dep cache cleared**: the running dev server keeps serving the old pre-bundle in `node_modules/.vite/deps` after `npm install` — a page reload only re-loads the page, so an SDK upgrade silently keeps the old behavior. Stop the server, `rm -rf node_modules/.vite`, restart.
- **Non-USDC bridging requires App Kit ≥1.15.0** — 1.11.0–1.14.0 hard-code `token: z.literal('USDC')` in the bridge schema, so EURC/wETH/cirBTC fail with `Invalid parameters: token: Invalid literal value, expected "USDC"`; 1.15+ accepts USDC + known symbols + bytes32 token ids. `src/services/__tests__/bridgeTokenSdkContract.test.ts` pins this against the real (unmocked) SDK.
- **Live Arc Testnet non-USDC routes (measured 2026-10-14):** EURC ↔ Ethereum Sepolia, Base Sepolia and Avalanche Fuji; wETH/cirBTC ↔ Ethereum Sepolia only. USDC routes anywhere CCTPv2 goes. USDC route checks resolve locally, but non-USDC support is queried from Circle's CCTP-X provider (network required). Full matrix, rule and evidence: `docs/cctp-arc-testnet-route-matrix.md`.
- **Non-USDC routability is a pair property with two gates** (`bridge.mjs`): both chains must be CCTP-X eligible (their SDK chain definition carries `cctpx.serviceAddress` — only domains 0/1/2/3/6/7/26 on testnet) **and** Circle's paginated registry (`/v2/cctpx/tokens`, walk `nextPageAfter`) must list the token with a deployment on both domains. Ineligible pairs fail definitively (`not supported for token`), registry failures are retryable (`could not complete the route check`) — never cache the latter as a verdict. The registry's `enabled` flag is ignored by the SDK.
- **`src/config/bridgeRouteMatrix.ts` is the single source of truth for that pair rule** — the Bridge tab's token list and both chain selectors are derived from it (an unsupported pair resets the token to USDC, and a token the pair cannot carry is simply absent from the dropdown — no explanatory banner). Don't re-derive routes from a token's chain presence. Guard rails: `src/config/__tests__/bridgeRouteMatrix.test.ts` (offline, pins the matrix to the real SDK chain defs + recorded registry rows) and `npm run verify:cctp-routes` (live; exit 1 = drift, 2 = registry rate-limited).
- **USDC's chain set is measured, not inferred from CCTPv2 support** — `USDC_BRIDGE_CHAINS` lists the chains a live Arc Testnet ↔ X bridge resolved on (all 12 selectable chains, both directions, measured 2026-10-14); `USDC_EXCLUDED_CHAINS` records why anything else is left out (today only Solana Devnet: CCTP supports it, this app cannot deliver there). A chain added to the selector must be measured before `isBridgeRouteSupported('USDC', …)` accepts it; the offline suite pins the list to `BRIDGE_SELECTABLE_CHAINS`.
- **Non-USDC bridges must keep `useForwarder: true`** — passing a destination adapter (which makes `bridgeService` send `useForwarder: false`) fails with `CCTPx buys forwarding in the quote ... cannot be turned off`. `BridgeModal` correctly forwards on all three estimate/execute paths.
- **Stop-the-world for dep changes:** after `npm install`, restart with `npm run dev -- --force` (or delete `node_modules/.vite`) — a plain restart can keep the same `?v=` dep URL, so open tabs keep executing the old SDK from cache and the old bug appears to persist.
- **The Circle-UCW direct bridge splits by mechanism, and `getUcwBridgeMechanism` (in `bridgeRouteMatrix.ts`) is the split.** A UCW wallet can only submit encoded challenge calldata, and Circle splits the contracts on purpose ("USDC and EURC bridging continues to use CCTP v2 (`cctp.v2.*`) actions, not CCTPx"):
  - `cctp-v2` — USDC **and EURC** through `TokenMessengerV2.depositForBurn(WithHook)` in `bridgeUcwService.executeUcwBridgeTransfer` (token address + decimals now come from `getBridgeTokenAddress`/`getBridgeTokenDecimals`; the function throws for anything else).
  - `cctpx` — wETH and cirBTC through `bridgeUcwCctpxService.executeUcwCctpxBridge`, which does **not** hand-roll the call: it runs App Kit's own encoder (`prepareAction(...).getCallData()`, no signer) and hands the resulting `{to,data,value}` to the wallet, plus a `token.approve` to the token manager Circle's registry names. Re-deriving `0x780c5acf crossChainTransfer` by hand would be a second implementation of a fund-moving call.
  - `null` — never offered; native `ETH` is explicitly `null` because wrapping needs an EIP-1193 provider to sign `deposit()`, which a UCW wallet does not have.
- **A UCW token list is the pair rule AND `canUcwBridgeTokenFrom(chain, token)`** (mechanism available + the token's own contract on the source chain) — `BridgeModal` filters the dropdown with it and refuses the pair in `handleTransfer`, so a token the source cannot deliver is unofferable rather than merely rejected.
- **CCTP-X fees are paid, never deducted.** Circle documents non-USDC fees as "paid in native gas on the source blockchain" so "the recipient receives the full transferred amount": the quote's `feeTotalAmount` is sent as the challenge's native `amount` (`msg.value`), which on Arc is USDC with **18** decimals and on the Sepolias ETH (decimals come from `CHAIN_NATIVE_MAP`, never a hardcoded 18). `BridgeModal` therefore shows `0.00` Net Received haircut for a CCTP-X route and discloses Circle's relayer fee in the Source Network Fee row via `quoteUcwCctpxRelayerFee`; the CCTP v2 fast/forward fee estimate must not be used there — it is a different, wrongly-denominated number.
- **CCTP-X addresses come from Circle's registry on every run** (`/v2/cctpx/tokens`, `bridgeUcwCctpxService`), and only the **source** row's `tokenAddress`/`tokenManagerAddress` are encoded into the approve + transfer — the destination row is only evidence the token exists on both domains. Offline guards pin the measured proxy (`0x63753E…077`), the approve delegate and the `0x780c5acf` pass-through: `src/services/__tests__/bridgeUcwCctpxPlan.test.ts`.
- **Unsupported pairs must be unofferable, not merely rejected** — `isBridgeRouteSupported` gates the CTA (`ROUTE NOT SUPPORTED`), `handleTransfer` and the copilot's bridge action; chain hints from other entry points pass through `isBridgeSelectableChain`, so a Solana balance cannot become the tab's source chain. Add a new bridge surface by reading `bridgeRouteMatrix`, never by listing tokens per chain.
- **Only USDC bridges can charge custom fees** — CCTP for non-USDC routes ignores `customFee`, so `bridgeService` applies it for USDC only.
- **No WBTC on Arc; the Bitcoin asset is `cirBTC`.** App Kit token names are case-sensitive (`wETH`, `cirBTC`); `normalizeBridgeToken` maps `WETH`→`wETH`, `BTC`→`cirBTC` and defaults to `USDC`.
