# AGENTS.md

Guidance for agents working in this repo (Arcis / `arc-mini-app`, Arc Testnet chain ID 5042002).

## Arc & CCTP bridging — verified facts

- **Arc Testnet bridging is not USDC-only.** Standard CCTP moves USDC (every CCTP domain except BNB Smart Chain); "CCTP for non-USDC" adds EURC plus configurable tokens (cirBTC, WETH). Arc's CCTP domain is `26` for both paths. Gateway's unified balance is USDC-only.
  - Sources: https://docs.arc.io/integrate/exchanges/cctp-bridging, https://developers.circle.com/cctp/expanded-assets/concepts/supported-chains-and-domains
- **Non-USDC CCTP routes are EVM-only** (Solana unsupported) and route-specific: both domains must trust each other and the token must be configured on both. Don't assume a token works on a route — check `https://iris-api-sandbox.circle.com/v2/cctpx/tokens`.
- **Local EVM simulators cannot validate Arc bridging** — Arc docs state they don't replicate EIP-7708 `Transfer` events, the USDC precompile, or blocklist enforcement. Test against Arc Testnet only.
- **`docs.arc.network` redirects to `docs.arc.io`** — the live docs host is `docs.arc.io` (skills and root `llms.txt` still use the old hostname).

## x402 paid calls — payer facts

- **A Circle user-controlled wallet can pay, because this app creates it as an EOA.** `api/ucw.ts` passes `accountType: "EOA"`, so Circle's typed-data challenge returns a plain 65-byte ECDSA signature that the server's `recoverTypedDataAddress` (`api/x402.ts`) verifies against the wallet address. `src/services/x402/ucwPaymentSigner.ts` adapts the hook's `signTypedData` into the x402 signer, and `resolveX402Payer(authSource, signer)` is the single gate: `evm` → `external_eoa`, `ucw` + signer → `ucw_eoa`, passkey/MSCA → `null`. Do not add a second per-surface rule.
- **The Circle challenge receives JSON, but `BatchEvmScheme` signs uint256 fields as `bigint`** — `JSON.stringify` throws on those, so the adapter converts them to decimal strings, which encode to the same EIP-712 hash. Pinned against the real (unmocked) SDK by `src/services/x402/__tests__/ucwPaymentSigner.test.ts`.
- **Circle's signTypedData validator is go-ethereum's encoder, so `types` must declare `EIP712Domain` and the body must be JSON.** It hashes the domain with `HashStruct("EIP712Domain", domain)` and rejects a domain carrying more fields than the declaration: `there is extra data provided in the message (0 < 4)` — that is 0 declared vs 4 domain fields, not a bad message. `src/services/ucwTypedData.ts` (`prepareCircleTypedData`) is the single preparer: it declares the canonical domain type (name, version, chainId, verifyingContract, salt — viem's order) and converts `bigint` uint256 fields to decimal strings. It is applied by the Gateway burn-intent service, the x402 adapter and `useUserControlledWallet.signTypedData` itself, is idempotent, and leaves hashes unchanged (tests pin hash equality plus recovery through the settlement route's typed data). Never hand a Circle challenge a payload that skipped it.
- **Passkey/MSCA payers stay blocked on purpose.** The server verifies the payer with `recoverTypedDataAddress` only; it implements no ERC-1271 path, so a smart-account signature cannot settle. A UCW payer also has no EIP-1193 chain to probe: the challenge route pins the ARC-TESTNET wallet and a wrong-domain signature fails ecrecover server-side, so `x402Readiness` reports the network as satisfied rather than unknown for `ucw`.
- **Copilot and AI Services both spend through `executeX402Call(..., payerKind, ucwSigner)`** — the optional 6th argument carries the Circle signer; without it a `ucw_eoa` payer is refused before any request goes out (`paymentOrchestrator` never creates an authorization for a signer-less payer).
- **A fee cannot be deducted from a paid call, so fee-bearing calls settle to the treasury and providers withdraw from it.** One EIP-3009 authorization names exactly one payee, and Circle's facilitator settles it verbatim, so `protocolFeeBps` cannot be skimmed from a payment that already pays the provider. `src/config/x402/treasury.ts` (`resolveSettlementRoute`) is the single routing rule: `feeBps === 0` → the provider (direct, no escrow), otherwise → `X402_TREASURY_ADDRESS` (fallback `VITE_EVM_TREASURY_ADDRESS`), and a fee-bearing call with no usable treasury refuses with 503 rather than paying the provider gross. Official manifests all charge `OFFICIAL_PROTOCOL_FEE_BPS = 50`; `splitSettlementAmount` does the split in micro-USDC (`feeMicros = floor(gross × bps / 10_000)`), and the provider is credited only the net. `api/_utils/x402Payout.ts` pays a withdrawal from the treasury with `X402_TREASURY_PRIVATE_KEY`, which must derive to the treasury address (a mismatch is a refusal). The withdraw endpoint reserves the ledger balance first, then pays; a definitive failure refunds the reservation (`refundWithdrawMicros`) and frees the nonce, an *unconfirmed* broadcast keeps both reserved. `PendingProviderSettlement.recipientAddress` is the payee Circle reports against — reconciliation matches `toAddress` to it, not to the provider — and `escrowed: false` marks a direct provider payment so it can never be withdrawn a second time.
- **Manifest addresses are not always correctly checksummed**, so viem's `isAddress` (strict EIP-55 for mixed case) rejects some of them: normalize with lowercase → `getAddress` (`safeChecksumAddress`, and `normalizeAddress` in `treasury.ts`). A strict `isAddress` check there silently disabled the treasury route.
- **Provider listings and earnings withdrawals follow the same EOA rule as payments.** `resolveProviderSigner` (`src/services/x402/providerAuthorization.ts`) is the single provider-side gate: injected EOA → `signTypedData`, `ucw` + challenge signer → `createUcwChallengeSigner` (`src/services/ucwChallengeSigner.ts`, shared with the x402 adapter), passkey/MSCA → refusal (the server only recovers). `src/services/x402/serviceRegistration.ts` builds the `ServiceRegistration` payload (domain, types, nonce, 5-minute deadline) and `withdrawProviderEarningsApi` builds `ProviderLedgerAuthorization` through the same module; omitting its `options` argument keeps the historical injected-only behavior for existing callers. `owner`/provider must be the signing wallet: the payout field cannot substitute for it, because the server requires `owner === listing.ownerAddress === provider.address`.

## Repo conventions & quirks

- **`.env.example` is the structural source of truth for the local `.env`** — both list the same keys in the same section order (`PRIVATE_KEY` is kept only in `.env`, and the template's §5 NOTE explains that the server never reads it; it is the Foundry deploy key). Every variable the code reads is documented there, including the legacy aliases `VITE_NETWORK`/`APP_ENV` (for `VITE_APP_ENV`). `X402_TREASURY_ADDRESS`/`X402_TREASURY_PRIVATE_KEY` are the only fee-settlement settings: an empty treasury address falls back to `VITE_EVM_TREASURY_ADDRESS`, and an empty payout key makes fee-bearing services answer 503 rather than collect fees they could not pay out. The documented LLM path is `OPENROUTER_API_KEY` + `OPENROUTER_MODEL`;but the paid `llm` engine reads only `OPENROUTER_API_KEY`.
- **Adding or removing a key in `.env` needs a real dev-server restart.** Vite logs `.env changed, restarting server...`, but a key that did not exist when the process booted stays invisible to `api/**` handlers (the API plugin's per-request `loadEnv` does not refresh it) — the symptom is a health check reporting a credential as missing while `.env` clearly has it. Stop and start the dev server, then re-check the endpoint; changing an existing value is picked up per request.
- **The x402 smoke-test echo upstream lives in `smoke/ucw-echo`** (deployed copy: `https://site-7639e6df17d44e5e8798cdb475b52e7f.freebuff.page/`). `api/x402.ts` requires a community upstream's host to be in `X402_UPSTREAM_HOST_ALLOWLIST` **and** its response to be a JSON object carrying a non-`UNAVAILABLE` `status` string; ready-made echo services (`httpbin`, `postman-echo`) return neither, so a payment against them is accepted and then voided. `npm run preflight:ucw-smoke -- --live` probes that contract.

- **A paid `llm` x402 service needs a JSON-mode model and a budget that fits its reasoning.** `src/services/x402/llmEngine.ts` sends `max_tokens: X402_LLM_MAX_OUTPUT_TOKENS` (default 1600) and **retries once** when the provider reports `finish_reason: "length"`: a reasoning model spends an unpredictable share of the budget on hidden reasoning, so a small cap returns `content: null` and the service answers `UNAVAILABLE`, which the tollgate voids with 503 *"The service has no available result to return"* (no charge). Measured: `deepseek/deepseek-v4.1-flash` fails ~5/5 at 400 tokens, succeeds 5/5 at 1600 (1 of 5 needed the retry, worst call ~29s end to end); The engine names the cause instead of blaming the schema.

- **AI Services hero-card figures derive from shared server data, never from a browser-local tally.** `src/services/marketplaceHeroStats.ts` computes Paid Calls, User Savings (`acceptedCalls × $0.05 Web2 baseline − ledger volume`) and Protocol Fee (`ledger volume × protocolFeeBps`) from `PlatformStatsSnapshot`; an unreadable ledger yields a dash, not a zero. Avg. Latency comes from `GET /api/x402/latency` (`api/_utils/x402Latency.ts`), which measures Arc Testnet RPC round-trip time server-side and caches one reading in the shared store (`arcis:x402:latency:v1:<env>`, 60 s TTL) — the per-service `serviceTelemetryService` probes stay browser-local (they power per-service cards and sorting) and must not feed the hero card. `ecosystemStatsService`'s localStorage counters are per-device and must not be presented as protocol metrics.
- **The reporting & risk agents share one institutional report envelope.** `src/services/x402/institutionalReport.ts` is the single definition (`arcis.institutional-report/v1`): deterministic `reportId`, `coverage` (measured/expected reads), a data-quality grade derived **only** from coverage, `freshness`, a severity-graded `riskRegister` (evidence, threshold, remediation) and `disclosure`. All four agents (`arc-portfolio-risk-exposure`, `arc-yield-vault-analytics`, `arc-vault-yield-tax-report`, `arc-cross-chain-gateway-flow-indexer`) return it under `report`; `riskFlags` is derived from the register for older callers. Do not add a per-service flag list or a second grading rule — extend the register. The grade never encodes risk: a fully measured concentrated portfolio is grade A with a HIGH finding. Normative contract and per-agent thresholds: `docs/institutional-report-contract.md`.
- **`llms.txt` at the repo root is Arc's docs index, not project documentation.**
- **Circle skills are duplicated byte-for-byte** in `.agents/skills/` and `skills/plugins/circle/skills/` (17 shared skills, verified identical). Apply any Circle skill edit to both; `.agents/skills/` additionally carries 7 non-Circle skills (`banner-design`, `brand`, `design`, `design-system`, `slides`, `ui-styling`, `ui-ux-pro-max`) that exist only there.
- **Bridge tab chains are intentionally narrower than Gateway's**: `BRIDGE_SELECTABLE_CHAINS` filters out Solana (balances, delivery verification and address handling on that surface are EVM-only), though Solana remains in `GATEWAY_SUPPORTED_CHAINS`.
- **Dependency changes need the Vite dep cache cleared**: the running dev server keeps serving the old pre-bundle in `node_modules/.vite/deps` after `npm install` — a page reload only re-loads the page, so an SDK upgrade silently keeps the old behavior. Stop the server, `rm -rf node_modules/.vite`, restart.
- **Non-USDC bridging requires App Kit ≥1.15.0** — 1.11.0–1.14.0 hard-code `token: z.literal('USDC')` in the bridge schema, so EURC/wETH/cirBTC fail with `Invalid parameters: token: Invalid literal value, expected "USDC"`; 1.15+ accepts USDC + known symbols + bytes32 token ids. `src/services/__tests__/bridgeTokenSdkContract.test.ts` pins this against the real (unmocked) SDK.
- **Live Arc Testnet non-USDC routes (measured 2026-10-14):** EURC ↔ Ethereum Sepolia, Base Sepolia and Avalanche Fuji; wETH/cirBTC ↔ Ethereum Sepolia only. USDC routes anywhere CCTPv2 goes. USDC route checks resolve locally, but non-USDC support is queried from Circle's CCTP-X provider (network required). Full matrix, rule and evidence: `docs/cctp-arc-testnet-route-matrix.md`.
- **Non-USDC routability is a pair property with two gates** (`bridge.mjs`): both chains must be CCTP-X eligible (their SDK chain definition carries `cctpx.serviceAddress` — only domains 0/1/2/3/6/7/26 on testnet) **and** Circle's paginated registry (`/v2/cctpx/tokens`, walk `nextPageAfter`) must list the token with a deployment on both domains. Ineligible pairs fail definitively (`not supported for token`), registry failures are retryable (`could not complete the route check`) — never cache the latter as a verdict. The registry's `enabled` flag is ignored by the SDK.
- **`src/config/bridgeRouteMatrix.ts` is the single source of truth for that pair rule** — the Bridge tab's token list and both chain selectors are derived from it (an unsupported pair resets the token to USDC, and a token the pair cannot carry is simply absent from the dropdown — no explanatory banner). Don't re-derive routes from a token's chain presence. Guard rails: `src/config/__tests__/bridgeRouteMatrix.test.ts` (offline, pins the matrix to the real SDK chain defs + recorded registry rows) and `npm run verify:cctp-routes` (live; exit 1 = drift, 2 = registry rate-limited).
- **USDC's chain set is measured, not inferred from CCTPv2 support** — `USDC_BRIDGE_CHAINS` lists the chains a live Arc Testnet ↔ X bridge resolved on (all 12 selectable chains, both directions, measured 2026-10-14); `USDC_EXCLUDED_CHAINS` records why anything else is left out (today only Solana Devnet: CCTP supports it, this app cannot deliver there). A chain added to the selector must be measured before `isBridgeRouteSupported('USDC', …)` accepts it; the offline suite pins the list to `BRIDGE_SELECTABLE_CHAINS`.
- **Non-USDC bridges must keep `useForwarder: true`** — passing a destination adapter (which makes `bridgeService` send `useForwarder: false`) fails with `CCTPx buys forwarding in the quote ... cannot be turned off`. `BridgeModal` correctly forwards on all three estimate/execute paths.
- **Stop-the-world for dep changes:** after `npm install`, restart with `npm run dev -- --force` (or delete `node_modules/.vite`) — a plain restart can keep the same `?v=` dep URL, so open tabs keep executing the old SDK from cache and the old bug appears to persist.
- **The Circle-UCW direct bridge splits by mechanism, and `getUcwBridgeMechanism` (in `bridgeRouteMatrix.ts`) is the split.** A UCW wallet can only submit encoded challenge calldata, and Circle splits the contracts on purpose ("USDC and EURC bridging continues to use CCTP v2 (`cctp.v2.*`) actions, not CCTPx"):
  - `cctp-v2` — USDC **and EURC** through `TokenMessengerV2.depositForBurn(WithHook)` in `bridgeUcwService.executeUcwBridgeTransfer` (token address + decimals now come from `getBridgeTokenAddress`/`getBridgeTokenDecimals`; the function throws for anything else).
  - `cctpx` — wETH and cirBTC through `bridgeUcwCctpxService.executeUcwCctpxBridge`, which does **not** hand-roll the call: it runs App Kit's own encoder (`prepareAction(...).getCallData()`, no signer) and hands the resulting `{to,data,value}` to the wallet, plus a `token.approve` to the token manager Circle's registry names. Re-deriving `0x780c5acf crossChainTransfer` by hand would be a second implementation of a fund-moving call.
  - `null` — never offered; native `ETH` is explicitly `null` because wrapping needs an EIP-1193 provider to sign `deposit()`, which a UCW wallet does not have.
- **A UCW token list is the pair rule AND `canUcwBridgeTokenFrom(chain, token)`** (mechanism available + the token's own contract on the source chain) — `BridgeModal` filters the dropdown with it and refuses the pair in `handleTransfer`, so a token the source cannot deliver is unofferable rather than merely rejected.
- **CCTP-X fees are paid, never deducted.** Circle documents non-USDC fees as "paid in native gas on the source blockchain" so "the recipient receives the full transferred amount": the quote's `feeTotalAmount` is sent as the challenge's native `amount` (`msg.value`), which on Arc is USDC with **18** decimals and on the Sepolias ETH (decimals come from `CHAIN_NATIVE_MAP`, never a hardcoded 18). `BridgeModal` therefore shows `0.00` Net Received haircut for a CCTP-X route and discloses Circle's relayer fee in the Source Network Fee row via `quoteUcwCctpxRelayerFee`; the CCTP v2 fast/forward fee estimate must not be used there — it is a different, wrongly-denominated number.
- **CCTP-X addresses come from Circle's registry on every run** (`/v2/cctpx/tokens`, `bridgeUcwCctpxService`), and only the **source** row's `tokenAddress`/`tokenManagerAddress` are encoded into the approve + transfer — the destination row is only evidence the token exists on both domains. Offline guards pin the measured proxy (`0x63753E…077`), the approve delegate and the `0x780c5acf` pass-through: `src/services/__tests__/bridgeUcwCctpxPlan.test.ts`.
- **Unsupported pairs must be unofferable, not merely rejected** — `isBridgeRouteSupported` gates the CTA (`ROUTE NOT SUPPORTED`), `handleTransfer` and the copilot's bridge action; chain hints from other entry points pass through `isBridgeSelectableChain`, so a Solana balance cannot become the tab's source chain. Add a new bridge surface by reading `bridgeRouteMatrix`, never by listing tokens per chain.
- **Only USDC bridges can charge custom fees** — CCTP for non-USDC routes ignores `customFee`, so `bridgeService` applies it for USDC only.
- **No WBTC on Arc; the Bitcoin asset is `cirBTC`.** App Kit token names are case-sensitive (`wETH`, `cirBTC`); `normalizeBridgeToken` maps `WETH`→`wETH`, `BTC`→`cirBTC` and defaults to `USDC`.

## UI design system & visual guidelines (DESIGN.md)

- **Strict adherence to `DESIGN.md` for all UI/UX work:** Arcis implements an "Aave Luxury + Arc Blockchain Obsidian" aesthetic. Never use generic or ad-hoc Tailwind colors (e.g., `bg-blue-600`, `text-green-500`). Use the design system's tokens (`--color-brand-*`, `--primary-colors-*`, `--earned-green`, `--purple-1`).
- **Typography pairing:** Space Grotesk for metrics/amounts (`tabular-nums`), Space Mono for badges/eyebrows/hashes, Inter for body/forms, Outfit/DM Sans for display headers.
- **Card & Button primitives:** Build upon `.ub-hero-card`, `.arc-card`, `.arc-btn`, `.ub-action-btn`, and `.glass-panel`. Always check `DESIGN.md` and `src/index.css` before introducing new UI components.
